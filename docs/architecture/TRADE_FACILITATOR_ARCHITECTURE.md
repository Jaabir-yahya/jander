# Trade Facilitator Architecture

**Hub-and-spoke model: Single WABA orchestrates trades between buyers and sellers on personal WhatsApp.**

This architecture document defines "The Trade Facilitator" model: one central WhatsApp Business Account (WABA) as the hub, buyers and sellers on personal WhatsApp, with platform orchestrating flows, payments, and notifications while absorbing Meta's constraints and monetizing per successful trade.

**Reference**: This document extends [`ARCHITECTURE.md`](./ARCHITECTURE.md) with the Trade Facilitator model. See [`BUILD_PLAN.md`](./BUILD_PLAN.md) for stage-gated execution plan.

## Core Model: Hub + Two Personal Sides

### Architecture Overview

```
┌─────────────────────────────────────────────────────────────┐
│                   Trade Facilitator Hub                      │
│              (Single WABA - Your Platform)                   │
│                                                               │
│  ┌──────────────┐      ┌──────────────┐      ┌──────────┐ │
│  │   Webhooks   │      │    n8n       │      │ ERPNext  │ │
│  │   Receiver   │ ───> │  Workflows   │ ───> │   DB     │ │
│  └──────────────┘      └──────────────┘      └──────────┘ │
│                                                               │
│  ┌──────────────┐      ┌──────────────┐      ┌──────────┐ │
│  │  WhatsApp    │      │   M-Pesa     │      │ Escrow   │ │
│  │    Flows     │      │   Daraja     │      │  Logic   │ │
│  └──────────────┘      └──────────────┘      └──────────┘ │
└─────────────────────────────────────────────────────────────┘
           │                      │
           │                      │
    ┌──────▼──────┐        ┌──────▼──────┐
    │  Buyer A    │        │  Seller B   │
    │ (Personal   │        │ (Personal   │
    │  WhatsApp)  │        │  WhatsApp)  │
    └─────────────┘        └─────────────┘
```

### Key Components

**Single WABA as Hub:**
- All conversations go through your business number
- Becomes the trusted "Local Trade Bot"
- Matches recommended "shared inbox / broker" patterns in WhatsApp commerce guides
- Centralized webhook processing, routing, and logic

**Buyer Side:**
- Starts chat with your bot
- Uses **WhatsApp Flows** / button menus (minimal typing → low literacy friendly)
- Receives **M-Pesa payment link / STK push** generated by your backend
- Confirms delivery, triggers payout to seller

**Seller Side:**
- Gets templated notifications: "Buyer wants X, reply Confirm / Reject"
- Manages orders by replying with structured options (not free text)
- Receives payout after buyer confirmation

**Platform (You):**
- Own webhooks, routing, and escrow logic
- See all trades in one place (ERPNext / custom DB)
- Control payouts to sellers after buyer confirmation
- Monetize per successful trade

## Meta Constraints & Design Decisions

### 1. Verification & Conversation Limits

**Constraint:**
- Unverified WABA: **250 unique conversations/day** (buyer + seller = 2 conversations per trade)
- Limited template use (only session messages within 24h)
- Full scaling requires: registered business, domain, privacy policy, site verification

**Design Decision:**
- **Stage 1**: Live within 250 conversations/day = ~125 trades/day maximum (unverified)
- **Stage 2**: Pursue verification (CoI, KRA PIN, site + privacy policy) as parallel "infra" task
- **Verified WABA**: 1,000–2,000+ conversations/day capacity
- Design capacity for **500–1,000 trades/day** (verified) = 1,000–2,000 conversations/day

**Implementation:**
- Track conversation windows per user (24h window from last message)
- Queue outbound messages if limit approaching
- Alert when 80% of daily limit reached
- Verification checklist as Stage 1 gate

---

### 2. Template Rules & Message Windows

**Constraint:**
- Any outbound message **outside 24h** since last user message must use pre-approved templates
- "Forwarded context" must fit into templates, not raw chat copy
- Template approval takes 24–48 hours

**Design Decision:**
- **Core Template Set** (Stage 1 - 5 templates):
  1. `new_order_to_seller` - "Buyer {{buyer_name}} wants {{product_name}} × {{quantity}} for KSh {{total}}. Reply CONFIRM or REJECT."
  2. `payment_link_to_buyer` - "Pay KSh {{amount}} for order {{order_id}}. Click to pay: {{stk_push_link}}"
  3. `payment_confirmation` - "Payment received! Order {{order_id}} confirmed. Seller will dispatch soon."
  4. `delivery_confirmation_request` - "Did you receive order {{order_id}}? Reply YES to confirm delivery and release payment to seller."
  5. `order_status_update` - "Order {{order_id}} status: {{status}}. {{details}}"

**Template Strategy:**
- All notifications use templates (never raw text outside 24h window)
- Context embedded in template variables: `{{buyer_name}}`, `{{product_name}}`, `{{order_id}}`
- Template approval workflow: Submit → Track → Use when approved
- Template versioning: Track v1, v2, A/B test variations

**Message Window Management:**
- Track last message timestamp per user (buyer/seller)
- Within 24h window: Use session messages (no template needed)
- Outside 24h window: Use templates only
- Alert users approaching 24h window (keep conversation active)

---

### 3. Low-Literacy UX Design

**Constraint:**
- Voice notes are hard for bots to process accurately
- Free text typing is error-prone for low-literacy users
- Recommended best practice: **quick replies, lists, and buttons** in WhatsApp Flows

**Design Decision:**
- **WhatsApp Flows** for critical steps (structured, button-based):
  - "Pick product" → List with images
  - "Confirm quantity" → Buttons (+1, +5, -1, Cancel)
  - "Confirm delivery area" → List templates (CBD, Eastleigh, Westlands, etc.)
  - "Delivery confirmation" → Yes/No buttons
  - "Seller response" → Confirm/Reject buttons

**Flow Design:**
```
Buyer Flow:
1. Product Discovery → WhatsApp Flow: Browse catalog (images, prices)
2. Add to Cart → Flow: Quantity selector (+1, +5, -1)
3. Checkout → Flow: Delivery area selector (CBD, Eastleigh, etc.)
4. Payment → Flow: M-Pesa STK push button
5. Delivery Confirmation → Flow: Yes/No button

Seller Flow:
1. Order Notification → Template: "New order {{order_id}}"
2. Accept/Reject → Quick Reply: CONFIRM / REJECT
3. Mark Ready → Quick Reply: READY
4. Payout Notification → Template: "Payment released for order {{order_id}}"
```

**Fallback:**
- Only fall back to human review for complex free-text/voice
- Voice notes routed to review queue (low confidence → human)
- Free text only for optional notes (delivery address details)

### 4. Cost Per Conversation

**Constraint:**
- WhatsApp charges per **24h conversation window** per user
- Trade Facilitator model uses **two windows** per trade:
  - Buyer A conversation window
  - Seller B conversation window
- Each window = 1 paid conversation

**Cost Model:**
- **Per Trade Cost**:
  - Buyer conversation: 1 conversation window
  - Seller conversation: 1 conversation window
  - Reminders/retries: +0.5 conversations (on average)
  - **Total: ~2.5 conversations per trade** (worst case)
  
- **SMSLeopard Pricing** (Kenya):
  - KSh 1,999/mo starter (10K messages) = ~KSh 0.20 per message
  - Per-conversation: ~KSh 0.50–1.00 (conversation window pricing)
  - Direct Meta: Lower per-conversation (~$0.005–0.01 per conversation)

- **Platform Cost Per Trade**:
  - WhatsApp conversation cost: KSh 1.00–2.50 per trade (2.5 conversations × KSh 0.50–1.00)
  - Hosting/automation: KSh 0.10–0.50 per trade (n8n, Supabase, ERPNext)
  - M-Pesa transaction fee: KSh 0 (absorbed by buyer)
  - **Total platform cost: KSh 1.10–3.00 per trade**

**Pricing Strategy:**
- **Transaction Fee**: KSh 50–100 per successful trade (2–5% of average order value)
  - Covers: WhatsApp cost (KSh 2.50) + Platform cost (KSh 1.00) = KSh 3.50
  - Margin: KSh 46.50–96.50 per trade
  - Break-even: ~50 trades/month to cover fixed costs (KSh 1,999 SMSLeopard)
  
- **Freemium Tiers**:
  - **Free**: First 10 trades/month free (onboarding incentive)
  - **Basic**: KSh 2,000/mo for up to 100 trades (KSh 20/trade effective)
  - **Growth**: KSh 5,000/mo for up to 500 trades (KSh 10/trade effective)
  - **Scale**: Custom pricing for 500+ trades/month

## Data Model

### Core Tables

**Trades Table** (Central entity):
```sql
CREATE TABLE trades (
  trade_id TEXT PRIMARY KEY, -- Format: TR20260109001
  buyer_phone TEXT NOT NULL,
  seller_phone TEXT NOT NULL,
  product_id TEXT NOT NULL,
  product_name TEXT NOT NULL,
  quantity INT NOT NULL,
  unit_price DECIMAL NOT NULL,
  total_amount DECIMAL NOT NULL,
  delivery_area TEXT, -- CBD, Eastleigh, Westlands, etc.
  status TEXT DEFAULT 'pending', -- pending, confirmed, paid, dispatched, delivered, completed, cancelled
  created_at TIMESTAMPTZ DEFAULT NOW(),
  confirmed_at TIMESTAMPTZ,
  paid_at TIMESTAMPTZ,
  dispatched_at TIMESTAMPTZ,
  delivered_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  buyer_conversation_id TEXT, -- WhatsApp conversation ID for buyer
  seller_conversation_id TEXT, -- WhatsApp conversation ID for seller
  payment_mpesa_ref TEXT, -- M-Pesa receipt number
  payout_mpesa_ref TEXT, -- M-Pesa payout reference (to seller)
  platform_fee DECIMAL, -- Transaction fee (KSh 50-100)
  payout_amount DECIMAL -- Amount to seller (total_amount - platform_fee)
);
```

**Buyers Table**:
```sql
CREATE TABLE buyers (
  buyer_id TEXT PRIMARY KEY,
  phone TEXT UNIQUE NOT NULL,
  name TEXT,
  preferred_delivery_area TEXT,
  total_trades INT DEFAULT 0,
  total_spent DECIMAL DEFAULT 0,
  last_trade_at TIMESTAMPTZ,
  last_message_at TIMESTAMPTZ, -- Track 24h conversation window
  conversation_window_expires_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Sellers Table**:
```sql
CREATE TABLE sellers (
  seller_id TEXT PRIMARY KEY,
  phone TEXT UNIQUE NOT NULL,
  name TEXT,
  business_name TEXT,
  mpesa_till_number TEXT, -- For payouts
  total_trades INT DEFAULT 0,
  total_revenue DECIMAL DEFAULT 0,
  total_payouts DECIMAL DEFAULT 0,
  last_trade_at TIMESTAMPTZ,
  last_message_at TIMESTAMPTZ, -- Track 24h conversation window
  conversation_window_expires_at TIMESTAMPTZ,
  status TEXT DEFAULT 'active', -- active, suspended, inactive
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Products Table** (Seller catalog):
```sql
CREATE TABLE products (
  product_id TEXT PRIMARY KEY,
  seller_id TEXT REFERENCES sellers(seller_id),
  name TEXT NOT NULL,
  description TEXT,
  price_kes DECIMAL NOT NULL,
  image_url TEXT, -- WhatsApp media URL
  category TEXT, -- Fabric, Electronics, Food, etc.
  active BOOLEAN DEFAULT TRUE,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Conversations Table** (Track conversation windows):
```sql
CREATE TABLE conversations (
  conversation_id TEXT PRIMARY KEY,
  user_phone TEXT NOT NULL, -- Buyer or seller phone
  user_type TEXT NOT NULL, -- 'buyer' or 'seller'
  trade_id TEXT REFERENCES trades(trade_id),
  started_at TIMESTAMPTZ DEFAULT NOW(),
  last_message_at TIMESTAMPTZ DEFAULT NOW(),
  expires_at TIMESTAMPTZ, -- 24h from last_message_at
  message_count INT DEFAULT 0,
  status TEXT DEFAULT 'active' -- active, expired, closed
);
```

**Payments Table**:
```sql
CREATE TABLE payments (
  payment_id TEXT PRIMARY KEY,
  trade_id TEXT REFERENCES trades(trade_id),
  amount_kes DECIMAL NOT NULL,
  mpesa_ref TEXT, -- M-Pesa receipt number
  payment_type TEXT DEFAULT 'stk_push', -- stk_push, paybill, till
  status TEXT DEFAULT 'pending', -- pending, completed, failed
  paid_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Payouts Table**:
```sql
CREATE TABLE payouts (
  payout_id TEXT PRIMARY KEY,
  trade_id TEXT REFERENCES trades(trade_id),
  seller_id TEXT REFERENCES sellers(seller_id),
  amount_kes DECIMAL NOT NULL,
  mpesa_ref TEXT, -- M-Pesa payout reference
  status TEXT DEFAULT 'pending', -- pending, completed, failed
  paid_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

## Workflow Design

### Trade Lifecycle Flow

**1. Discovery → Intent**
```
Buyer → WhatsApp Bot: "I want to buy"
Bot → Buyer: WhatsApp Flow (Product Catalog)
Buyer → Flow: Selects product, quantity, delivery area
Flow → Backend: Creates trade (status: pending)
```

**2. Order → Seller Notification**
```
Backend → Seller: Template "new_order_to_seller"
  Content: "Buyer {{buyer_name}} wants {{product_name}} × {{quantity}} for KSh {{total}}. Reply CONFIRM or REJECT."
Seller → Bot: Quick Reply "CONFIRM" or "REJECT"
Bot → Backend: Updates trade status
```

**3. Confirmation → Payment**
```
If Seller CONFIRMS:
  Backend → Buyer: Template "payment_link_to_buyer"
    Content: "Pay KSh {{amount}} for order {{trade_id}}. Click to pay: {{stk_push_link}}"
  Buyer → Flow: Clicks STK push button
  M-Pesa → Backend: Payment webhook
  Backend → Buyer: Template "payment_confirmation"
  Backend → Seller: Template "payment_confirmation"
  Backend: Updates trade status to "paid"
```

**4. Dispatch → Delivery**
```
Seller → Bot: Quick Reply "READY" (when order ready)
Backend → Buyer: Template "dispatch_notification"
Seller → Bot: Quick Reply "DISPATCHED" (when dispatched)
Backend → Buyer: Template "delivery_confirmation_request"
  Content: "Did you receive order {{trade_id}}? Reply YES to confirm delivery and release payment to seller."
Buyer → Bot: Quick Reply "YES" or "NO"
```

**5. Delivery → Payout**
```
If Buyer confirms delivery:
  Backend → Seller: M-Pesa B2C payout (payout_amount = total_amount - platform_fee)
  Backend → Seller: Template "payout_notification"
  Backend → Buyer: Template "order_completed"
  Backend: Updates trade status to "completed"
  Backend: Records payout transaction
```

## SMSLeopard vs Direct Meta (For Trade Facilitator)

### Why SMSLeopard Fits This Model

**Advantages:**
1. **M-Pesa Payment**: Pay in KSh, no FX friction
2. **Local Support**: 
   - Template crafting & submission assistance
   - WhatsApp Flows configuration help
   - Faster template approval (typically 24h vs 48h)
3. **SMS Fallback**: When data is off, still notify seller/buyer with critical events
   - Matches informal market realities (spotty 4G)
   - Critical for time-sensitive notifications (payment, delivery)
4. **Regional Expertise**: Kenya-specific compliance, local regulations
5. **Operational Simplicity**: Less ops overhead for solo dev

**Trade-off:**
- Slight markup vs direct Meta (~10–20% premium)
- But gains: Faster template approval, less ops overhead, support when WhatsApp behavior/regulations change

**When to Use Direct Meta:**
- If Meta direct access becomes available in Kenya
- If cost optimization critical at scale (500+ trades/day)
- If building for global deployment beyond Kenya
- If need advanced features only in direct API

**Architecture Support:**
- Both providers supported via environment variable
- Same webhook structure, same API patterns
- Swap provider by changing `WHATSAPP_PROVIDER` env var

## Cost Per Trade Calculation

### Assumptions

- **Average Order Value**: KSh 2,000 (typical informal trade)
- **Conversations Per Trade**: 2.5 (buyer + seller + reminders)
- **WhatsApp Cost Per Conversation**: KSh 0.75 (SMSLeopard average)
- **Platform Cost Per Trade**: KSh 0.50 (hosting, automation)

### Cost Breakdown

**Per Trade Costs:**
- WhatsApp conversations: 2.5 × KSh 0.75 = **KSh 1.88**
- Platform costs: **KSh 0.50**
- **Total cost per trade: KSh 2.38**

**Revenue Per Trade:**
- Transaction fee: KSh 50–100 (2.5–5% of KSh 2,000 average)
- **Net margin per trade: KSh 47.62–97.62**

### Break-Even Analysis

**Fixed Costs (Monthly):**
- SMSLeopard: KSh 1,999/mo (10K messages)
- Supabase: KSh 3,000/mo (production tier)
- n8n: KSh 0 (free tier) or KSh 2,000/mo (paid)
- ERPNext: KSh 2,000/mo (optional, Week 9+)
- **Total fixed: KSh 4,999–6,999/mo**

**Break-Even Point:**
- With KSh 50 transaction fee: 4,999 ÷ 47.62 = **~105 trades/month**
- With KSh 100 transaction fee: 4,999 ÷ 97.62 = **~51 trades/month**

**Scale Targets:**
- **Month 1–3**: 50–100 trades/month (break-even)
- **Month 4–6**: 200–500 trades/month (KSh 20K–50K MRR)
- **Month 7–12**: 500–1,000 trades/month (KSh 50K–100K MRR)
